# injector (`src/injector`)

Library and CLI for everything outside the client: find clients, inject the agent, read what it publishes, send input, run Luau scripts.

Real code only on Windows. On other targets the same API compiles to stubs returning "clients can only be reached from Windows or Wine" (the `offline` module in `sandbox.rs`) so the loader still builds natively; on Linux the real work is `injector.exe` under Wine.

## Session cache and the agent's worker

- `win.rs` keeps a `Session` per pid for 500 ms (process handle, mapped state block, the agent's events, a write view of the shared memory that header reads and overlay frames use, and the request mutexes), so a read, request or overlay frame doesn't reopen and remap them; `forget(pid)` drops it on agent load/unload, a protocol mismatch or a request timeout. `load` reads the header without the session, so its process never holds the old agent's mappings across a reload. `input.rs` caches the `JagRenderView` window per pid and checks it with `IsWindow`.
- Every pure memory read (`npcs`, `players`, `ground_items`, `projectiles`, `spot_anims`, `widget`, `widget_children`, `sub_interfaces`, `game_state`, `item_container`, `varc`, `chat_messages`, `world_select`) first asks the agent's worker thread (`ask_worker`, see `work_event_name` in [ipc-protocol.md](ipc-protocol.md)) and decodes its postcard answer; the same `decode::worker` function runs through `ReadProcessMemory` when it can't answer. Either way each read is a syscall, so per-object decoders copy an actor or projectile with one read (`decode::memory::Snapshot`) and open a hash table once for many lookups (`ipc::read::Table`). `npcs` takes about 0.09 ms against 2.4 ms that way. The first call after an agent reload may fall back.
- `ground_items` keeps item names in a per-process cache: a name never changes while the client runs, so only unseen ids cost a game-thread request.

## Luau sandbox

`sandbox::run_with_modules` creates a Lua state bound to one pid, with `dofile` and `loadfile` removed and a sandboxed `require`. The globals are defined in `sandbox.rs`; scripts use them through the Luau lib's `host.luau` (a separate project), never raw.

- Queries and actions return `(result, err)`.
- `connection` and `game_state` raise instead ("no client selected", "agent isn't loaded in the client"); `run <pid>` exits at startup when the agent is missing or on another protocol, so scripts never see a nil connection.
- `time()` is ms since start, `clock()` seconds since local midnight, `unix_time()` seconds since the Unix epoch; `form(spec)` shows a settings dialog (defaults when no handler); the kinds are `form::KINDS`, of which `equipment`, `inventory` and `prayer` (`LAYOUT_KINDS`, `HOST_API` 10) have no default and get their value, a layout the loader keeps per script, or null, from the loader (see [loader-gui.md](loader-gui.md)); `equipment` and `inventory` fields may list `required` items and `prayer` fields `locked` prayers (`HOST_API` 15), checked by `form::validate` (`form::Required`: one or more `ids`, an equipment item's worn items `slot` from `form::EQUIPMENT_SLOTS`, an inventory item's optional slot 0 to 27, no slot named twice, `min` at most `max` or both 0, `doses` unique numbers from 1).
- `report_stats(experience, gold, custom?)` writes a `form::STATS_PREFIX` line (`\u{1e}STATS {json}`) through the print sink; the loader sums these between heartbeats and sends them to the API. Experience must be 0 or more; values are rounded to integers. Outside a store run the loader drops them. The gains are since the last call, not totals; runtime is measured by the loader, never reported by the script.

### HTTP

Break and sleep config: the loader owns it (`antiban.rs`, `Config`: `breaks_enabled`, `sleeps_enabled`, `breaks`, `sleeps`; a field left out is Auto, picked by the lib from the account's biometrics) and writes it as a `\u{1e}ANTIBAN <json>` line, among the first lines (before the script) and again at any time (the stdin thread applies it with `antiban::set`, which raises a version). `antiban_config()` returns the current one (the default when the loader sent none) with that `version`; the lib's `Antiban.sync_config` re-plans when it changes. `\u{1e}SKIP break|sleep <index>` lines ("Skip next" in the Breaks tab) queue in `antiban::push_skip` and `antiban_skips()` drains them. Configs that don't validate (`Config::validate`) are dropped. Biometrics (`biometrics.rs`): `murmur2a(text, seed?)` and `biometrics_profile(name)` (24 bytes); the lib caches the profile and does the random draws from it.

`http_request(options)` returns `(response, err)`: `options` is `{ url, method?, headers?, body?, timeout? }` (`http::Request`), the response `{ ok, status, headers, body }`. The injector can't reach the network itself: it writes a `\u{1e}HTTPREQ <json>` line and waits for the loader's one line answer on stdin, the way `bank_pin_enter` asks for the PIN (`main.rs` installs the handler only when the loader's first lines include `http::CAPABILITY_PREFIX` (after `form::PINS_PREFIX`); without it the call returns "HTTP requests aren't available"). The loader checks the URL's host against the user's whitelist and makes the request, so what a script can reach is decided outside the sandbox (see [loader-gui.md](loader-gui.md)). Request bodies are at most 1 MB and responses 8 MB, both text; the timeout is 15 s unless given, 60 s at most. It raises nothing for a failed request (`nil, err`); a 404 is still a response.

`item_prices(items)` (`HOST_API` 17) returns `({ ItemPrice? }, err)` in the order of `items`, ids or names (any case, trimmed). It goes through the same handler as `http_request`, to the wiki real-time prices API, whose URL the loader sends before the script (its config's `prices_url`, on a `prices::PREFIX` line) and always allows; without that line, as in a `run` started by hand, the call returns `nil, err`. The item list is fetched once a day and the latest prices every 10 minutes, lazily on a call, into a process-wide cache (`prices::PRICES`), so each `run` downloads them itself. A refresh that fails keeps the old data and isn't tried again for a minute, so a down API isn't asked on every call; with no data yet the call returns `nil, err`. An id the item list doesn't have is named through `item_names` (when there is a client) and looked up by that name, which turns noted and placeholder ids into the tradeable item; a name several items share resolves to the lowest id. The requests carry the loader's `User-Agent`, which the wiki asks to be descriptive.

`entry_swaps()` (`HOST_API` 18) returns `{ swaps, alt }`, the client's own menu entry swaps for the logged-in account (`entry_swaps.rs`): each is a list of `{ target, options }` read from `entryswaps.dat` and `entryswapsalt.dat` in the account's folder (a version line, then one `Target,Option,Option` line each; `entry_swaps::parse`). The client applies a swap when it runs a left click and leaves the menu it lists unchanged, so `menu()` and the up-text don't show it. The folder is found by duplicating the handles of the client process (`win::find_user_folder`, handle values up to `HANDLE_SCAN_LIMIT`) until one is a file in a `users\<digits>` folder below the profile folder at the drive root (so a numeric Windows user name doesn't match), and is remembered per pid and account name (`SWAP_FOLDER`); the files are read on every call, and a missing one is an empty list. It fails while the client has no such file open (not logged in). The lib's `Minimenu.left_click_index` applies them.

`players()` gives each player `movement` (`HOST_API` 19): the stand, turn left, turn right, walk, walk back, walk left, walk right and run sequences the server set for that player (`decode::world::PLAYER_MOVEMENT`). Its `pose` is one of them when nothing else holds the player, so a pose outside it is an obstacle, an emote or a ride in progress, whatever the weapon.

### Async input

`click_async`, `move_async`, `wind_mouse_async`, `type_text_async`, `mouse_down_async`, `mouse_up_async`, `scroll_async`, `key_down_async` and `key_up_async` queue the same input as their blocking twins on the script's `async_input::Worker` (one per `run`, created with the Lua state) and return immediately; jobs run in order. The script takes the input back with:

- any blocking input (`click`, `move`, `mouse_down`, `key_down`, ...), which cancels first;
- `input_cancel()`;
- the live menu reads `menu`, `menu_open` and `menu_layout` (not `menu_click`, a record of the last click).

Cancelling drops the queue, interrupts the running job's sleeps and returns once the worker is idle, so nothing is posted after it. A job always releases what it pressed: a cancelled click still sends the button up, `type_text` releases the key and the modifiers. Buttons and keys pressed by `*_down_async` jobs are tracked (`input_jobs.rs`, `Held`): `cancel` and shutdown release them, last pressed first, whether the worker was idle, paused or mid-move. `sleep_async(ms)` queues a pause (`Job::Wait`) for holding something down. `input_busy()`, `input_wait()` and `input_error()` (take and clear the last failed job's error; `input_wait` waits first) cover the rest. The worker is shut down when the script ends. New input code must sleep through `Pace` (`send_with`), not `thread::sleep`, or cancel can't interrupt it.

### `require`

- **With `--script <path>`** (the loader always passes it; a Windows path under Wine): `require("./x")` / `require("../x")` reads `x.luau`, `x.lua` or `x/init.luau` from disk, relative to the requiring file. Paths must start with `./` or `../`; modules are cached by normalized path. New lib files need no rebuild. `require("@lib/main/walker")` names a module by its path inside the lib root (the configured lib dir, else the `lib/` beside the script) from any file, script or lib module; the editor side is the `lib` alias in `scripts/.luaurc` and `lib/.luaurc`.
- **Otherwise** (piped script, or a bare name like `require("game_state")`): the lib compiled into the injector (`LIB_MODULES`, `include_str!` from the sibling `lib/` project, default `embedded-lib` feature). It is stale until a rebuild, new lib files must be added to `LIB_MODULES`, and `VOLCREN_LIB_DIR` (a `lib/` directory; under Wine a Windows path like `Z:\home\me\VOLCREN\lib`) reads those modules from disk instead. `--no-default-features` drops the embedded copy, so the build no longer reads `lib/`; the release workflow builds that way, since the loader always passes `--script`.

### Item change callbacks

`on_item_change(fn) -> id`, `off_item_change(id)` and `wait_item_change(ms)` (typed in the lib's `host.luau`) register Luau callbacks for the item log. The first callback makes an `ItemWatcher` (a subscriber of the log, see [ipc-protocol.md](ipc-protocol.md)). The script is one thread running Luau, so a callback can't interrupt it: `sleep` (replaced while a callback is registered) and `wait_item_change` block on the watcher's event instead of a timer, so they wake when the agent logs a change, run the callbacks for what was logged and go on sleeping for the rest of the time. A script that never sleeps never runs its callbacks. An error in a callback is an error in `sleep`.

### Packet callbacks

`on_packet(opcodes, fn, sent?) -> id`, `off_packet(id)` and `wait_packet(opcodes, ms, sent?)` do the same for the packet log: received packets by server packet id, or with `sent` the client's own by client packet id (0 to 255). They share one `PacketWatcher` whose filter is the union of every callback's ids and those of a running `wait_packet` (`Callbacks::refresh_packets`); it exists only while something wants a packet. `sleep`, `wait_item_change` and `wait_packet` wait on the item and packet watchers' events together (`wait_watchers`), so a script with both kinds gets both. `wait_packet` returns the first matching packet logged after the call (not one waiting from before it) or nil, after running the callbacks for everything read with it. A packet reaches Luau as `{sequence, time_ms, sent, opcode, length, payload}`, `payload` a string of the first 104 bytes (`length` is the whole). The ring holds a few seconds of a busy client's traffic, so a script that doesn't sleep for longer loses packets.

### Server tile and movement

`server_tile()` reads the local player's path head (`decode::state::server_tile`): the tile the server last put them on, ahead of the smoothed `position`. `movement()` reads the packet log's `Movement` block and the tick counter fresh, and returns `{x, y, plane, from_x, from_y, from_plane, moving, moved_tick, tick}` (`crate::Movement`); `nil` when the hook hasn't seen the player or the path head can't be read (logged out: the block keeps the last tile). The agent fills the block before taking each packet, so `moving` is exact even when the script was busy through several ticks, which Luau callbacks can't be: a queued tick callback reads the tile as it is now.

### Adding a global

1. Implement it in the injector and bind it in `sandbox.rs`.
2. Add the `offline` stub for non-Windows.
3. Add the type and wrapper to the Luau lib's `host.luau` and document it there (separate project).

## Gotchas

- Shared-state reads race with the agent: go through the ipc sequence-locked helpers.
- The agent tells synthetic input from real by the `SYNTHETIC` flag; post input only through `input.rs`.
