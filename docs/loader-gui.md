# loader (`src/loader`)

The user-facing desktop app (`eframe`/egui), a native binary. It never touches the client itself: a new capability goes in the injector (and usually the agent) first, then gets surfaced here.

## What it does

- Lists game clients; loads, reloads and unloads the agent; shows agent version, protocol, offsets state and a protocol mismatch warning.
- Runs each script as its own `injector run --script <path> <pid>` process, so a crashing script can't take the app down. Streams output, pauses, stops (escalating if ignored), renders script forms (`FormSpec`) and remembers their values. Opens `default.luau` from a `scripts/` folder next to the executable (or the sibling scripts project) on start.
- Requires a Discord sign-in to start: until signed in the window shows only a sign-in screen (and the log). Sign-in is PKCE over a loopback redirect to `127.0.0.1:5217`; the refresh token lives in the OS keyring, never in eframe storage. The header shows the account, balance and "Buy credits".
- Scripts tab (`Tab::Store`): lists the scripts the account can see, with price, online count and a disabled Run (with the reason on hover) when there's no access, not enough credits, no loaded client, or another script running. Run starts a session, downloads the live revision into memory, and runs `main.luau` through the normal script path.
- Community scripts (written by someone below scripter) are tagged `community` in the list, official ones `official`, and scripts that came from a share code say "shared with you". Testers and above get a Community checkbox that lists every community script (`GET /launcher/scripts?community=true`); they stay out of the default list. The redeem box takes a share code (checked locally as 64 hex digits), calls `POST /launcher/scripts/redeem` and refreshes the list; the server's message says if the code was invalid, expired or used. A granted script has "Remove from my account" (`DELETE /launcher/scripts/:id/grant`, two clicks). `API_VERSION` is 2: a loader that predates community scripts is told to update instead of running them without the warning.
- Before the first run of a community script, and again for every new revision of it, the loader shows a warning window. "Run anyway" is remembered per script and revision in the loader's local storage (`store::Confirmed`, key `community_confirmed`, one revision per script, at most 500 scripts). `session::prepare` refuses a community script whose started revision isn't the one that was confirmed, and ends that session, so a revision published after the warning never runs unseen. A failed start refreshes the list.
- Store script files are stored encrypted (AES-256-GCM); the session response carries the key and `session::decrypt_file` opens each file (a revision from before encryption has `key: null` and is plain). No store script is written to disk: its files stay in memory, are downloaded again on every start, and go to the injector over stdin (`MODULES` message, `Prepared::modules`), which resolves the script's `require("./name")` from them. The revision folder stays empty. For testers and above (`Me::can_view_source`) the entry file is also shown read-only in the Editor (`view_store_source`); everyone else never sees a store script's source.
- While a store script runs the loader sends a heartbeat every `heartbeat_seconds` (billing, online count, stats from `report_stats`). If the server says the session is over, the script is stopped and the reason shown; if no heartbeat succeeds for 4 minutes the script is stopped before the server's 5 minute timeout. The session is ended when the script stops, finishes or crashes, and on exit (with a 3 second limit; the server's sweep covers the rest). Pausing a store script does not pause billing.
- On start it fetches `latest.json` from the public `client` bucket and shows a Download/Dismiss banner when a newer version exists (`src/update.rs`). Releases are built and published by `.github/workflows/release.yml` on every push to `main`. Versions are `YYYY.MM.DD-<7 character commit>` (UTC commit date), embedded by `build.rs`; local builds use their checked out commit, or `dev` outside git, which never prompts an update. Store scripts run against the shared `lib/` in the cache (`src/libs.rs`): the newest lib in `lib/index.json` whose `requires_host` is at most the loader's `injector::HOST_API`. If a newer one exists that this loader cannot run, the script log warns to update the loader. Settings detection looks next to the executable first, so an installed release needs no `target/` folder.
- While a script runs, store or local (from the editor), its page (`Tab::Running`, `running_ui`) replaces both Scripts and Editor in the sidebar, named after the script (`running_title`), and opens when the script starts. It has Pause/Resume and Stop, and shows the script's settings form (`Form::show_inline`) instead of a modal window; the page goes away when the script ends (a store session's end, or the process exiting), back to Scripts, or to the Editor after a local run.
- Navigation is a neo-tree style sidebar like the webapp's (`sidebar_ui` in `app.rs`, row painting in `theme.rs`): Client, Scripts (or the running script), Editor, Development, Terminal, Accounts, Settings. It is always shown when the window is at least `SIDEBAR_MIN_WINDOW` wide; below that the header logo toggles it as a drawer (closed by picking a page, a click outside, or Esc).
- Accounts is a sidebar page (`src/accounts.rs`, `Tab::Accounts`): a list of saved game accounts, each a name, the SHA-256 of the lowercased, trimmed account name (`hash_name`; the name itself is never kept, scripts will recognise an account by hashing its name) and a four digit bank pin shown as asterisks. "Add account" opens a dialog (name, account name, pin; Cancel and Save on the right). Rows are edited in place: clicking a name renames it in place, the pin shows and edits it in place, the hash opens the dialog below. Edits only change the row's working copy; the row's Save button (beside Delete) is enabled while it differs from what is on disk and writes it. Delete needs a second click. The list is an `egui_extras` table: three equal columns and a fixed one for the buttons, with whole cells clickable. The add dialog and the dialog that opens when a row's hash is clicked ("Change account": just the account name) have "Load account from client" at the bottom left, which fills in the name of the account logged in on the selected client (`GameState::account_name`, the client's normalized name, which the display name override never changes; shown with spaces), and Cancel and Save at the bottom right. Changing a row's account only changes its working copy until the row's Save. `hash_name` normalizes like the client does (lowercase, spaces and hyphens as `_`), so the typed and the read name hash the same. Adding, saving a row and deleting write to `accounts.bin` in the data folder (`ProjectDirs` `com.volcren.Volcren`), sealed with AES-256-GCM (`nonce || ciphertext || tag`) under a random 32 byte key kept in the OS keyring (`volcren-loader` / `accounts-key`), created on the first save. If the file can't be opened (no keyring, missing or wrong key) the page says why and refuses to save, so the file isn't overwritten.
- Scripts' `http_request` goes through the loader (`src/http.rs`): the injector writes an `HTTPREQ` line, `Script::answer_http` makes the request on a thread of its own (a slow server doesn't freeze the window) and writes the one line answer back. The request is only made if its host is on the HTTP whitelist (`src/whitelist.rs`), which Settings edits: the Volcren hosts (those of `api_url`, `supabase_url` and `site_url` in the config) are listed as "Built in" and can't be removed, and "Add URL" opens a dialog for more. An entry is a host (`example.com`, matching any scheme, port and path; a pasted URL is cut down to its host) or `*.example.com` (its subdomains, not the domain itself); Delete needs a second click, as in Accounts. The user's entries are saved in eframe storage (`http_whitelist`), where no script can reach them. Redirects are followed by hand, at most 5, and each hop's host is checked too; `Authorization`/`Cookie` headers aren't sent to a different host than the first. The whitelist is copied when the script asks, so a change applies from the next request.
- Terminal is its own sidebar page between Development and Settings (`src/terminal.rs`, `Tab::Terminal`): the user's shell (`$SHELL`, `COMSPEC` on Windows) in the folder the loader was launched from, on a `portable-pty` pseudo-terminal, emulated by `alacritty_terminal` (the engine Zed uses) and drawn cell by cell in egui, so TUIs like Claude Code and Codex work. The shell starts the first time the page opens and lives until the app closes. Ctrl+Shift+C copies the selection and Ctrl+V pastes (Ctrl+V is not sent to the program); Shift+Enter sends a newline. Mouse reports go to a program that asks for them (hold Shift to select anyway).
- Backend endpoints (`api_url`, `supabase_url`, the public `anon_key`, optional `site_url`) are compiled in from `src/loader/config.json` (`api/config.rs`); the `API_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SITE_URL` environment variables override them at run time. There is no `.env`.
- Edits scripts with Luau syntax highlighting.
- On Run, compares the file on disk with what the editor last synced (`ScriptFile::disk`: set on open, save, startup) and prompts to reload if it changed; the prompt also warns about unsaved edits.
- Dev tools: RuneLite-style checkboxes (`DEV_TOGGLES` in `app.rs`) that draw scene layers through `injector::scene_tiles_next_frame`, once per frame the client presents (`TilesWorker`); a checkbox with no entry in `DEV_LAYERS` isn't ported yet.
- Development has tabs (`DevTab` in `app.rs`): Tools (game state and the checkboxes above) and Inspectors, which holds a tab per inspector (`InspectorTab`: Widget, Var, Script, Inventory, Packet; the names below keep "Inspector" for the thing itself). The Var Inspector, which also holds the collapsed Varps section (read one varp, the known varps, or what changed since the last read) above its log (`Inspector` in `src/vars.rs`: with Enable on, `poll_vars` reads all varps every `POLL_EVERY`, diffs them against the previous read and logs changes under `Tick N` headers like RuneLite's; a changed varp logs its varbits that changed (looked up once per varp with `backend::varbits_of`) and then the varp if bits remain unexplained; the first read, and the first after a logout, is only a baseline; the VarClientInt and VarClientStr boxes list the client variables the scripts change, from the varc log (`injector varc-changes`; the poll job reads it with the varps, the first read only marks the place, and a log that can't be read is a warning, not an error), shown by index since varcs have no names here), the Script Inspector (`Inspector` in `src/script_log.rs`: with Enable on, `poll_script_log` reads the client's script log (`injector scripts <pid> <since>`, `backend::script_runs`) every `POLL_EVERY` and lists a run per row (columns Tick, Script, Arguments, Time) with its duration once the end entry has been read (an end entry belongs to the latest unended row of its depth, and is dropped when a shallower row comes first), nested runs indented, `Trigger <type>` for component and menu events whose script id isn't known, and the tick the run started in on the first run of each tick; scripts show as `Script <id>` until the Load names button is clicked; it downloads RuneLite's `cs2-scripts` repository as one zip on a worker thread (`Names::download` in `script_names.rs`; the cache has no script names, only a hash of each, so nothing is bundled) and keeps `name (id)` for every script it names in memory only, the commit it is from shown under the buttons (the ids are the cache's, so the names are right for the build the repository was decompiled from); the Blacklist box drops scripts, by id or (once loaded) name, as they arrive (default `6697, 4730`, the ones an idle account runs every frame), keeping the last 10000 runs) the Inventory Inspector (`Inspector` in `src/inventory.rs`: with Enable on, `poll_inventory` reads the client's item log (`injector item-changes <pid> <since> <wait ms>`, `backend::item_changes`; the agent hooks the client's container slot writer). A read with nothing new blocks (up to `WAIT_FOR_CHANGE`) on an event the agent sets when it logs a change, so there is no timer: the next read starts when the last one returns, and on Linux the waits go through a helper of their own (`Lane::Events`). The first read marks the place in the log (`injector::ITEM_CHANGES_NOW`) and reads every container once (`injector containers`, `backend::item_containers`) as a baseline; after that the inspector applies the logged slot changes to its own copy and never rescans the containers. A snapshot is the copy after the changes one container got in one game tick, with that tick; a log that skipped changes (overwritten, or a new agent's) makes the next read a baseline again. Container names come from `game-vals` kind INV, item names from `item-names` and stackability from the item definition (`item-stackable`), each looked up once. Like RuneLite's, snapshots wait in a pending list until Refresh moves them into the tree (25 per container, `KEEP`); picking a tick shows what was added and removed against the snapshot before it, summed by item id with a non stackable item listed once per copy, then every slot as text since the loader has no item sprites) and the Widget Inspector (`Inspector` in `src/widgets.rs`, `widgets_ui` in `app.rs`: Refresh reads every open interface with `injector widget-tree <pid>` (`backend::widget_tree`; the first look at the tab reads it too) and links it as RuneLite does, each node lettered R (a top of the root interface), S (a component, under the one its parent field names), D (a dynamic child, under its owner) or N (the top of an interface opened inside a component), D before S before N; "Hide hidden" leaves out hidden widgets and their children; the right side lists RuneLite's fields in its order for those the agent reads (id with the group's name from `game-vals` kind INTERFACE, type, content type, parent, self hidden and hidden, text, text colour, opacity, font, text shadow, item id and quantity, sprite, tiling, filled, original position and size, the position and size modes, line height, text alignment, relative position, size, canvas location, bounds, scroll, no click through; `WidgetDetail` in `decode/src/widgets.rs`). The selected widget is boxed in cyan on the client while the tab shows, through the `widget:x,y,w,h,rrggbb` layer of the scene tiles worker. RuneLite's picker widget has no counterpart; "Follow mouse" looks at the client's mouse about ten times a second and selects the smallest widget there instead. RuneLite's other fields (model id, type, animation and rotation, border type, item quantity mode, name, target verb, drag settings, no scroll through, the listeners, ...) are not read yet, and none can be edited) and Packet Inspector (`Monitor` in `src/packets.rs`, `packets_ui` in `app.rs`). The Enable checkbox starts reading: `poll_packets` reads the selected client's packet log (`injector packets <pid> <since>`, `backend::packets`) every `POLL_EVERY` and keeps the last `KEEP` packets, also while another tab is showing. Received and sent packets list as a table (`LogTable` in `app.rs`, which the Var and Script Inspectors use too: a header that stays visible, resizable columns, rows drawn only while shown, long cells clipped) with the columns Time, direction (←/→, sent in the link colour), Opcode, Length, Name, Fields (decoded) and Hex; Received/Sent boxes and the Filter box filter: opcodes or packet names to show, `40, VARP_LARGE`, or to hide, `!40 !PLAYER_INFO` (`Filter` in `src/packets.rs`; a name stands for its packet in one direction and is matched in any case, `UNKNOWN` for every packet without a name). The Names menu next to it (`packet_names_menu` in `app.rs`) lists the known names with a search box, and each click cycles a name through show only, hide and off by rewriting the Filter text, which stays the single source of truth. Follow keeps the list at the newest packet. Clicking a packet shows it in the detail pane: a hex dump with ASCII, the leading bytes as big endian byte/short/int, and Copy hex. Opcodes are raw numbers: they change with game updates. Received packets with a known layout show their fields decoded (value and wire kind) above the hex dump, with their name when there is one, and the identifiers the client's handler touches; a payload that doesn't fit the layout or the expected size is flagged, not guessed at. The layouts come from the client itself: with Enable on, the monitor asks the selected client for what its agent published (`injector packet-layouts <pid>`, `backend::packet_layouts`, once per client and again every 5 seconds until the agent has), and `packet_defs::Table::from_client` turns that into the table `Monitor::table` hands the UI. Until then, and for a client without it, the table shipped in `src/packet_defs.tsv` (generated from the Java client, see [reverse-engineering.md](reverse-engineering.md)) is used; it also supplies names, kept by opcode only while every one of the 151 packet sizes matches the shipped table's (so the opcodes haven't moved; the sent names need that too), and after an update that moved them only for a packet whose size and layout (with fields) are shared with exactly one packet of the shipped table and one of the client's. Packets without a layout stay raw. Sent packets come only from the shipped table, where `names.tsv` names the ones that were worked out (`S<opcode>`, so far only `NO_TIMEOUT`, the keepalive). A sent packet's length excludes its opcode byte.
- Persists `Settings { dll, helper }` (paths of `agent.dll` and `injector.exe`), auto-detected next to the executable or in `target/x86_64-pc-windows-gnu/{release,debug}`. Also persists the mouse cursor preference (`Cursor`, storage key `cursor`), which is passed to `injector load` so the agent starts with it (the injector leaves it in an `AGENT_CURSOR_<pid>` mapping the agent reads while building its header).

## Layout

| Path | Contents |
| --- | --- |
| `src/app.rs` | The whole UI and its state. |
| `src/script.rs` | Script processes: spawn, stdio pumping, pause, stop, `ScriptEvent` (`Output`, `Form`, `Stats`, `Finished`). |
| `src/form.rs` | egui rendering of a form spec. |
| `src/api/` | The launcher API: `config.rs` (embedded endpoints), `auth.rs` (PKCE, loopback listener, token exchange/refresh, keyring), `client.rs` (`Api`: blocking calls, 401 refresh-and-retry), `models.rs`, `error.rs` (`ApiError`). Everything blocks, so `app.rs` runs it through `api_job` threads. |
| `src/account.rs` | `Auth` state and the sign-in round trip. |
| `src/http.rs`, `src/whitelist.rs` | A script's HTTP requests (host check, manual redirects, size and time limits) and the HTTP whitelist with its Settings section. |
| `src/accounts.rs` | The Accounts page: entries, hashing, pin check, encrypted file, list and dialog UI. |
| `src/store.rs` | The Scripts tab: list, filters, redeem box, community tags, price and balance text, and `Confirmed`, the community warnings the user accepted. |
| `src/update.rs` | Update check against `latest.json` and the version comparison. |
| `src/session.rs` | Starting a store run: the cache folder (the shared lib, and an empty `<script-id>_<revision>` folder per script that the entry path points into), download into memory with name/checksum checks, pruning; and `Beat`, the heartbeat state machine (retries with backoff, give-up, stats pending). |
| `src/packets.rs` | The packet monitor's buffer and filter (`Monitor`, `Filter`); the UI is `packets_ui` in `app.rs`. |
| `src/terminal.rs` | The Terminal page: pty session, key and mouse encoding, painting. |
| `src/highlight.rs` | Luau highlighter. |
| `src/backend/mod.rs` | `Settings`, `Target`, `Scan`; re-exports one function set (`connection`, `load`, `state`, `input`, `draw`, ...) from the compiled backend, so `app.rs` is platform independent. |
| `src/backend/native.rs` | Windows: calls the `injector` library directly. |
| `src/backend/wine.rs` | Linux: finds each client's Wine prefix (by the client executable's name, `CLIENT_EXES`), runs one `injector.exe serve` per prefix and talks JSON lines over stdio (`HELPER_TIMEOUT` 45 s). A helper answers one request at a time, so requests that wait for the client's next frame (the dev overlays) go to a second helper of their own (`Lane::Frames`). |

## Gotchas

- The loader depends on the `injector` crate, so the injector's non-Windows stubs must keep compiling.
- On Linux, anything that needs Win32 goes through the Wine helper protocol.
