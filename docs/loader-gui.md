# loader (`src/loader`)

The user-facing desktop app (`eframe`/egui), a native binary. It never touches the client itself: a new capability goes in the injector (and usually the agent) first, then gets surfaced here.

## What it does

- Lists game clients; loads, reloads and unloads the agent; shows agent version, protocol, offsets state and a protocol mismatch warning.
- Runs each script as its own `injector run --script <path> <pid>` process, so a crashing script can't take the app down. Streams output, pauses, stops (escalating if ignored), renders script forms (`FormSpec`) and remembers their values. Opens `default.luau` from a `scripts/` folder next to the executable (or, in a build under `target/`, the sibling scripts project) on start.
- Requires a Discord sign-in to start: until signed in the window shows only a sign-in screen (and the log). Sign-in is PKCE over a loopback redirect to `127.0.0.1:5217`; the refresh token lives in the OS keyring, never in eframe storage. The header shows the account, balance and "Add funds" (the website's balance page).
- Credits are shown at 1 = 1 EUR everywhere, written with the unit `CREDIT` like a currency code and never plural, as the website does (`api::models::credits_label`, "12.50 CREDIT": `credits_text` gives whole amounts without decimals, others with two to four decimals of the internal 10,000-per-euro unit; the account balance always shows all four, `balance_label`, "12.5000 CREDIT"; messages say "Not enough CREDIT"). `theme::credits` puts the amount and a smaller suffix ("/h") on one row. A script's price is its hourly rate in bold with the per-minute rate small beside it (`store::price_ui`). The header shows the balance and, while store scripts run from this loader, what they cost together an hour: each session's price plus its extra-session fee (`StoreRun::rate_per_hour`).
- Scripts tab (`Tab::Store`): lists the scripts the account can see, with price, online count and a disabled Run (with the reason on hover) when there's no access, not enough credits, or no free client. "Run on" (`run_target_ui`, also above the editor's Run) is a dropdown of the loaded, usable clients that aren't running a script, pre-picked when there is one (`run_target`): a client runs one script at a time, a store script on its way (quoted, waiting on a dialog or downloading) holds its client too, and the Client page's selection only serves the Client and Development pages. Run starts a session, downloads the live revision into memory, and runs `main.luau` through the normal script path. Run asks the server what the session would cost (`GET /launcher/scripts/:id/quote`, `App::start_at_quote`), since an author, a grantee or a tester pays 0 whatever the script lists and only the server knows the account's open sessions. The quote comes with the account as the server has it now (`session::quote`), so a top-up made on the website counts, and the Scripts page's Refresh reads the balance too. A quoted balance above the account's refuses the start in the log. A quoted fee, which means the account already has a session open anywhere and pays one (never tester+), opens an "Extra session" dialog first that says which instance this would be and what it adds an hour and a minute, the quoted price, and the total an hour and per 30 days, and the script starts only on Confirm. A disabled Run trusts the listing's `can_access`, which already weighs the balance: `StoreScript::blocked` only uses the balance to word a refusal. The dialog (`start_prompt_ui`, like the community warning shown from any page) also serves a restart, below.
- Community scripts (written by someone below scripter) are tagged `community` in the list, official ones `official`, and scripts that came from a share code say "shared with you". Testers and above get a Community checkbox that lists every community script (`GET /launcher/scripts?community=true`); they stay out of the default list. The redeem box takes a share code (checked locally as 64 hex digits), calls `POST /launcher/scripts/redeem` and refreshes the list; the server's message says if the code was invalid, expired or used. A granted script has "Remove from my account" (`DELETE /launcher/scripts/:id/grant`, two clicks). `API_VERSION` is 2: a loader that predates community scripts is told to update instead of running them without the warning.
- Before the first run of a community script, and again for every new revision of it, the loader shows a warning window. "Run anyway" is remembered per script and revision in the loader's local storage (`store::Confirmed`, key `community_confirmed`, one revision per script, at most 500 scripts). `session::prepare` refuses a community script whose started revision isn't the one that was confirmed, and ends that session, so a revision published after the warning never runs unseen. A failed start refreshes the list.
- Store script files are stored encrypted (AES-256-GCM); the session response carries the key and `session::decrypt_file` opens each file (a revision from before encryption has `key: null` and is plain). No store script is written to disk: its files stay in memory, are downloaded again on every start, and go to the injector over stdin (`MODULES` message, `Prepared::modules`), which resolves the script's `require("./name")` from them. The revision folder stays empty. The Editor never shows a store script's source.
- While a store script runs the loader sends a heartbeat every `heartbeat_seconds` (billing, online count, stats from `report_stats`). If the server says the session is over, the script is stopped and the reason shown; if no heartbeat succeeds for 4 minutes the script is stopped before the server's 5 minute timeout. The session is ended when the script stops, finishes or crashes, and on exit (with a 3 second limit; the server's sweep covers the rest). All of this runs on a thread per store run (`session::keep`), not in `ui()`: the window draws no frames while it is minimized or on a hidden workspace, and a session must survive that. A script's PIN, lamp and `http_request` requests are answered off the UI too, on the thread reading its output (`script::Host`), since a script blocks until it gets an answer. Only a form still waits for the window, because it needs a person, and the run's log shows what happened once frames are back. Pausing a store script does not pause billing. Signing out, by the button or because the server ended the sign-in, stops every script and ends the open sessions first (`App::stop_all`), since the sign-in screen has no Stop.
- Settings page, Transports section: a checkbox per type of transport (`injector::transports::TYPES`), saved in `Settings.transports`. It reaches the script as a `TRANSPORT_SETTINGS` stdin line before it starts and at once on a change (`Script::push_transport_settings`). The chooser honours it, and a script that needs a type calls `Transports.require_enabled`.
- Output panel buttons (`log_controls_ui` in `app.rs`) act on the open tab: Clear empties it, Copy all copies its shown text, and Save writes that text to a `.txt` file chosen in a save dialog (`save_log`), reporting the path or error in the loader's log. The panel builds its text's `LayoutJob` only when the tab, its revision, the font or a colour changes, and keeps the laid-out galley (`LogJob::laid_out`) while the wrap width and pixels per point stay the same and a one-space probe galley is still the one egui's galley cache returned, since egui replaces that cache whenever it rebuilds its font atlas.
- Settings page, "output lines": how many lines each output tab keeps (`Settings.log_lines`, saved with the settings), within `backend::LOG_LINES` (2000 to 10 000; a saved value outside it is clamped by `Settings::fill_missing`). A change applies at once to every open tab (`Log::set_keep`). A tab drops its oldest lines a quarter at a time once it holds a quarter more than that. The cap exists because a tab is one text widget, so Ctrl+A covers all of it, and egui lays out the whole of it again whenever a line is added: about 6 ms and 13 MB per thousand lines on a fast desktop CPU, so 10 000 lines costs around 60 ms per new line and 130 MB while the tab is open.
- Output text selection: dragging a selection above or below the output scrolls it, and keeps scrolling while the pointer is held there (`scroll_selection_past_edge`). The speed is the share crossed of the room between the output's edge and the window's (at most `SELECTION_SCROLL_RAMP`), up to `SELECTION_SCROLL_MAX` at the window's edge (`selection_scroll_speed`): the output sits at the bottom of the window, so a speed by plain distance was much slower down than up. egui's `TextEdit` scrolls to its cursor only when keys move it, never during a drag.
- Transport data (`src/transports.rs`): the loader asks upstream for its newest commit once a day and keeps the last 3 versions, each in its own folder under `<data dir>/transports/`, listed in `versions.json`. A new version is used only once every file has downloaded and parsed, and a script keeps the data it started with. The Settings page has "Check for update", and "Roll back", which drops the version in use and goes to the one before it, ending at the copy bundled with the loader. The daily check won't take a commit that was rolled back from, but the button will.
- Breaks tab: edits the global break and sleep config (`Settings.antiban`, saved with the loader's settings, the same for every script). Sub tabs Breaks and Sleeps each hold their editor and their queued rows. Editors in `breaks.rs` (`header`, `breaks_editor`, `sleeps_editor`; fields can be left on Auto, which the lib resolves from the account's biometrics); while a script runs, Update sends it live (`Script::push_antiban`) and the queued breaks and sleeps it reports are listed below with a "Skip next" each (`Script::skip_next`). Nothing is listed when no script runs. A script gets the saved config in its first lines when it starts (`injector::antiban::line`), so a loader needs a matching injector.
- On start it fetches `latest.signed.json` from the public `client` bucket, verifies the manifest against the embedded keys before parsing it, and shows a banner when its `build` (the commit's Unix time, embedded by `build.rs` as `VOLCREN_BUILD`) is later than this build's (`src/update.rs`; 0, a build outside git, never prompts). A bad signature is an error in the log and no banner. The update then installs by itself and the loader restarts (`update::installs_by_itself`), so users stay on the latest version: the whole window shows its progress (`updating_ui`), so nothing can start and be closed under the user, with "Skip for now" in case a download stalls, which cancels the download. An update never installs while another loader is open, since it replaces the files that one runs from: every loader holds a share of `loader.lock` in the data folder (`update::Instance`), and one that isn't alone waits for a click and then says to close the other. It waits for a click on the banner's "Update and restart" only if a run was active, starting or waiting on a dialog when the check answered (the button is disabled until none is), or if the loader was restarted with `--update-failed`, so a failure or a declined prompt can't repeat on every restart; either way the next start tries again. The check runs once per start, so a loader left open stays on its version until it restarts. `update::kind` decides the rest. Under a cargo `target/` folder the banner only informs. On Linux (`src/update/archive.rs`) the archive downloads and unpacks into `<install dir>/.update/`, its 4 files are renamed in (with hard links to undo a failure, when the old version stays and keeps running), and the new loader starts once this one has closed, so `save()` and `on_exit` run; an install dir that can't be written offers the old browser Download instead. On Windows (`src/update/msi.rs`) the MSI downloads to `<data dir>/update/` and its sha256 is checked; the loader copies itself there, starts the copy with `--finish-update` and closes. The copy, unelevated and outside the install, waits for it to exit, runs `msiexec /passive` with the install's own mode and folder (read from Windows Installer, since upgrades don't cross modes), and starts the installed loader as the normal user, with `--update-failed <message>` if the exit code calls for it; declining the UAC prompt of a per-machine install counts, which stops that start asking again. A copy that the MSI didn't install gets the browser Download. Either way the next start cleans up, and `backend::Settings::fill_missing` makes an install use the `agent.dll` and `injector` next to it, so a saved path can't pair it with another version. Releases, signing and the installer are in [releases.md](releases.md). Versions are `YYYY.MM.DD-<7 character commit>` (UTC commit date), for display; local builds use their checked out commit, or `dev` outside git. Store scripts run against the shared `lib/` in the cache (`src/libs.rs`): the newest lib in `lib/index.json` whose `requires_host` is at most the loader's `injector::HOST_API`. If a newer one exists that this loader cannot run, the script log warns to update the loader. Settings detection looks next to the executable first, so an installed release needs no `target/` folder.
- Several scripts run at once, one per client (`runs: Vec<Run>`; `Run` holds the process, the client, the store session if any, the form, its log and its XP, breaks and counters trackers). The Sessions page (`Tab::Sessions`, `sessions_ui`, between Editor and Development) lists every run with its status, client, run time, hourly rate (with whether it pays the extra-session fee and the fee paid so far, from the heartbeat's `rank`, `fee` and `fee_charged`), and Open, Pause/Resume, Stop and, once ended, Close, which takes the run and its log off the list; runs stay listed until closed. An ended store run also has Restart there and on its page, greyed out with the reason when its client is gone or busy, another start is under way or a dialog is open. Restart (`App::restart_run`, `session::restart_quote`) ends the old session again, which is safe to repeat and keeps it out of the count, then reads the script's listing (the community list only for tester+, who alone may ask for it) and `GET /launcher/scripts/:id/quote`. A script no longer listed, a lost access or too low a balance goes to the log and nothing starts. The dialog comes first when the quoted price differs from the old session's or the new session pays the extra-session fee (`session::asks_first`); the price compared is the quote's and not the listing's, since an author, a grantee or a tester pays 0 whatever the script lists. The community warning still applies to a new revision. The new run takes the same client and opens its page, and the old run and its log close only once the new one has started, so a failed restart leaves it listed. A run from the editor has no Restart. Each run is a row nested under Sessions in the sidebar (`theme::sidebar_child`, dimmed once ended) that opens its page (`Tab::Run` for `active_run`, `running_ui`), named after the script. A run's page opens when it starts and again when it asks for its settings. The page has Pause/Resume and Stop, and shows the script's settings form (`Form::show_inline`) instead of a modal window: one field under another, or with `columns` the checks in a column on the right, and in both the shown fields next to each other with the same `row` on one line (`Form::show_fields`, `show_row`): left to right, each as wide as it needs with text kept unwrapped, the spec's `row_gap` points apart (`ROW_GAP` by default), and one under another while the width the line took when last drawn that way (kept in egui temp memory) is wider than the space left; a label with `heading` 1 is drawn as egui's heading and with 2 bold, halfway between the body and heading sizes. Submitting the form answers the script's `Host.form` and the form stays on the Settings tab: the Start button becomes Update (enabled only while the values differ from what the script last got), which writes an `UPDATE` line to the script's stdin (`Script::push_update`, `App::push_form_update`). The injector reads stdin on a thread of its own, keeps the latest update and the script collects it with `Host.form_update()` (`HOST_API` 8); Pause/Resume stays beside it; the page stays after the script ends (a store session's end, or the process exiting) until the run is closed from the Sessions page.
- The running script's tabs (Settings, the layout tabs, XP Tracker, Breaks, Feedback for a store run) share one scroll area in `running_ui`, with a scroll position per tab, so whatever doesn't fit gets a scrollbar; the open tab is the run's (`Run::tools_tab`). The layout editors read from the run's client. The output panel at the bottom has a tab per run (`LogTab::Run`) beside the loader's, follows the open run, and a run's lines, forms, stats, breaks and requests are handled per run (`handle_script_events`), with the pin and lamp answers and HTTP requests served from the loader as before.
- Equipment, Inventory and Prayer tabs (`src/layouts.rs`): a form field of kind `equipment`, `inventory` or `prayer` (`injector::form::LAYOUT_KINDS`) adds that tab to the running script's page, and shows in the Settings tab as a dropdown of the script's saved layouts of that kind (`layouts::picker_ui`; the chosen name is what the form remembers, `Form::remembered`, and the script gets the layout's contents, `Form::submitted`, or null when none is chosen, so editing a chosen layout enables Update). Layouts are kept per script, by form title, in eframe storage (`layouts`, `AllLayouts`: `ScriptLayouts { equipment, inventory, prayer }`). Saved layouts this loader can't read (saved by a newer one, whose format it doesn't know) are never saved over (`layouts::load`, `LoaderApp::layouts_unreadable`): the stored text is copied to `layouts-unreadable-<unix seconds>.ron` in the data folder, the loader log says so, and the editor starts empty without saving. Without that, an older loader would read none and write the empty set over them. Two open loaders still each write their own copy of the whole storage file, so layouts saved in one can be overwritten by the other. Each tab (`layouts::equipment_ui`, `inventory_ui`) has a dropdown of the saved layouts plus "New layout", the name, Save (enabled while the draft differs and the name is free), Duplicate and Remove; above the grid, in a column as wide as the layout dropdown and the name box side by side, each under its label (`COLUMN_WIDTH`; Save, Duplicate and Remove share it in thirds, and `Editor::read_ui` puts the tab's hint, centred, and "Read from client" at its full width), with the equipment, inventory and prayer grids centred under it; the Inventory and Prayer tabs put the whole column in the middle of the tab (`centered_column`), and the Inventory tab's rune pouch (when there is one) and then the selected slot go below its grid, centred, with a two line hint (`App::read_layout`: a background read of container 94 or 93 with the items' names and stackability; for an inventory holding a rune pouch, the pouch's runes from varbits 29, 1622, 1623, 14285 and 1624, 1625, 1626, 14286 through enum 982, `Event::LayoutRead`). Only items read from a client go into a layout: there is no item list. A read also looks up each item that doesn't stack and whose name ends in a number in brackets (`injector::config::dose_of`: `Prayer potion(4)`, `Black mask (10)`) with `backend::item_doses` (`injector item-doses`, which reads every item definition in the cache only when one of the items has such a name, and groups the names by what precedes the number, leaving out notes, placeholders and bought copies), and gives it a dose setting that accepts its own dose (`layouts::add_doses`, `Doses`). A stack wants `min` to `max` (`Item`; a layout saved with the old single `quantity` loads it as both ends, `StoredItem`). The equipment grid is laid out as the worn items tab (head, secondary ammo; cape, amulet, ammo; weapon, body, shield; legs; hands, feet, ring). The secondary ammo cell (`SECONDARY_AMMO_SLOT`, past the container) is always there, since a layout can't know whether the account will have a bolt pouch or Dizana's quiver, and the lib ignores it without one: `layouts::read_secondary_ammo` reads it (a quiver, by item param 1910 on the worn cape or a carried item, from varps 4142 and 4141; else a carried bolt pouch's fourth stack from varbits 2476 and 2472 through enum 336), reading "Any" when nothing gives the slot and "Must be empty" when it is empty, and a layout saved without the slot, or made by hand, starts at "Any". In the grid: a click selects a slot, a right click empties an item's slot, and the selected slot shows its name and, when it holds no item, a dropdown of "Must be empty" and "Any" (greyed "any" in the grid), or the item's detail (`item_ui`): for a stackable, Min and Max boxes (equal is exactly that many, both 0 any amount; the end not being edited moves to keep min at most max), and for a dose or charge item a checkbox per number its family has (one stays ticked) and a Highest first / Lowest first dropdown, the accepted list kept in that order; changing one item's doses gives every item of its family in the layout the same setting (`share_doses`). The Equipment tab has two columns, centred in the tab together (`centered_width`) and stacked, the spell section under the rest, when the tab is narrower than the two columns plus their gap (both `COLUMN_WIDTH` wide): the header, hint, worn items grid and, under the grid, the selected slot's name and dropdown or amount on the left, and the layout's spell on the right: a spellbook dropdown, as wide as the column, with the spell columns centred under it (standard, ancient or Arceuus; the picked spell's book to start with, then the last choice, kept in egui memory) and only that book's combat spells (`AUTOCAST_SPELLS`, from the client's enum 1986 and each spell obj's params, the 24 px sprite included) in a column per element or family (`spell_column`: Wind, Water, Earth, Fire, Smoke, Shadow, Blood, Ice, Grasp, Demonbane; the standard book's spells without one, such as Magic Dart and the god spells, share an Other column), each listed weakest at the top by Magic level, one picked at a time across books; the section is "Autocast" when the weapon read from the client offered autocast (its category, varbit 357, in `AUTOCAST_WEAPON_CATEGORIES`, read with the worn items into `Equipment::autocast`) and "Spell to cast by hand" otherwise, and the script gets `spell` with the name, book, level and that flag, or null. The inventory grid is 4 x 7 with egui drag and drop to swap slots (a slot senses click and drag, so a plain click selects and a drag starts only after the pointer moves; `DragAndDrop::set_payload` on `drag_started`, a ghost icon under the pointer, `dnd_release_payload` on the target; not `dnd_drag_source`, whose own drag-only sense swallows clicks), the same right click and amount, and a Rune pouch row of up to 4 runes with amounts when the layout holds a pouch. Both draw item icons through the icon store, with the item's name's first letters until an icon arrives. A form's `required` items and `locked` prayers (`Form::rules`, `layouts::Rules`, parsed by `injector::form::required` and `locked` and checked by `form::validate`) apply to every layout of their kind: each frame a tab shows, its saved layouts and the draft are fitted to them, and so is the value the script gets (`Kind::value_of`). `Rules::fit_inventory` puts each required item in an inventory layout: one already there (locked, or the user's own with one of its ids) stays in its slot, the rest go to the slot the script gave or the first free one, and a locked item the script no longer requires becomes the user's; an inventory layout with no room for them shows why under the grid, can't be saved, and is greyed in the Settings dropdown with the reason (`Kind::unusable`), its value null. The user's own items of a required dose item's family take its doses (`Inventory::script_doses`; shown, not editable), so the lib sees them all as one item and counts each potion once. `fit_equipment` puts each in its slot, replacing what the layout had. A required item draws with a padlock in its top right corner (`paint_padlock`, painted shapes: a gold body with a keyhole and an arched shackle on a dark backing), can be dragged but not emptied, its detail says the script requires it, and "Read from client" keeps it where the user put it unless the client holds it elsewhere (`apply_inventory`). Its name and stackability come from a client (`App::describe_items` for `Rules::unknown`, `Event::ItemsKnown`, kept in `App::known_items` for the loader's life; a failed read isn't retried), until then it shows by id. The Prayer tab shows the prayer book as the tab lays it out (`PRAYERS`, by level, 5 to a row, each with the sprite the client's prayer tab uses, drawn through the icon store as `Key::Sprite`; the upgrades Deadeye, Mystic Vigour and Zeal, which take the slot and quick bit of Eagle Eye, Mystic Might and Piety once unlocked, are always shown too, since which an account has isn't known without reading it: the prayer data, sprites and unlock varbits come from the client's prayer objs (params 630, 1752, 1753, 1757) and `[proc,prayer_updatebutton]`, `[proc,script10190]` and `[proc,script10194]` in RuneLite's cs2-scripts): clicking a prayer puts it in the layout and takes out the ones it can't be on with (`Prayer::toggle`, by the `boost` flags: one of each stat, one overhead, and Chivalry, Piety, Rigour and Augury with no other stat prayer), a prayer above the client's Prayer level (from the XP tracker's reads, when a script runs) is dimmed but can be picked, a prayer the script controls (`Rules::blocks`: a `locked` one, or one sharing a `boost` flag with one, so locking Protect from Melee covers every overhead) is dimmed with a padlock, a click on it only selects it to show "The script controls this prayer: it can't be customised." under the grid, and `fit_prayer` keeps it out of every layout and read, and "Read from client" fills the layout with the prayers on now (each prayer's varbit) while "Read quick prayers" takes the quick prayer selection (the bits of varbit 4102; a bit shared by a base prayer and its upgrade is the upgrade when its unlock varbit is 1). A layout is only the set; the script's lib decides whether to turn them on or make them the quick prayers. `Editor<L>` holds a tab's state, one set per run (`Run::editors`): the open layout's index (none for a new one) with the name it is saved under, which finds it again when another run of the script changed the list, the draft, the selected slot and the read in flight; `Layout` is the trait both kinds share, and `to_value` the JSON the script gets (documented in the lib's `host.luau`: equipment slots with a `mode`, inventory slots by `slot`, `pouch`, each item with its `ids`, `min`, `max`, `doses` in the order to take them and `locked`, and a prayer layout's `locked`, every prayer the script controls).
- Navigation is a neo-tree style sidebar like the webapp's (`sidebar_ui` in `app.rs`, row painting in `theme.rs`): Client, Scripts (or the running script), Editor, Development, Terminal, Accounts, Settings. It is always shown when the window is at least `SIDEBAR_MIN_WINDOW` wide; below that the header logo toggles it as a drawer (closed by picking a page, a click outside, or Esc).
- Accounts is a sidebar page (`src/accounts.rs`, `Tab::Accounts`): a list of saved game accounts, each a name, the SHA-256 of the lowercased, trimmed account name (`hash_name`; the name itself is never kept, scripts will recognise an account by hashing its name), a four digit bank pin shown as asterisks and a lamp skill (a dropdown, "None" by default, that a script's `lamp_skill()` asks for with a `LAMPREQ` line, as `bank_pin_enter()` asks for the pin; "None" keeps a random event's lamp). "Add account" opens a dialog (name, account name, pin; Cancel and Save on the right). Rows are edited in place: clicking a name renames it in place, the pin shows and edits it in place, the hash opens the dialog below. Edits only change the row's working copy; the row's Save button (beside Delete) is enabled while it differs from what is on disk and writes it. Delete needs a second click. The list is an `egui_extras` table: three equal columns and a fixed one for the buttons, with whole cells clickable. The add dialog and the dialog that opens when a row's hash is clicked ("Change account": just the account name) have "Load account from client" at the bottom left, which fills in the name of the account logged in on the selected client (`GameState::account_name`, the client's normalized name, which the display name override never changes; shown with spaces), and Cancel and Save at the bottom right. Changing a row's account only changes its working copy until the row's Save. `hash_name` normalizes like the client does (lowercase, spaces and hyphens as `_`), so the typed and the read name hash the same. Adding, saving a row and deleting write to `accounts.bin` in the data folder (`ProjectDirs` `com.volcren.Volcren`), sealed with AES-256-GCM (`nonce || ciphertext || tag`) under a random 32 byte key kept in the OS keyring (`volcren-loader` / `accounts-key`), created on the first save. If the file can't be opened (no keyring, missing or wrong key) the page says why and refuses to save, so the file isn't overwritten.
- Feedback is a sidebar page after Accounts (`src/feedback.rs`, `Tab::Feedback`), and a running store script's page has a Feedback tab (`ToolsTab::Feedback`, store runs only) with the same controls for that run. The page lists the account's sessions of the last 24 hours (`GET /launcher/sessions`, `Api::recent_sessions`; fetched when the page or tab shows and the list is older than `REFRESH_EVERY`, after a run starts or ends, and on Refresh), newest first, each with its script, revision and times (UTC, cut to the minute). Each has a 1 to 10 score row (`POST /launcher/sessions/:id/score`; the account has one score per script, so the answer is shown on every listed session of that script) and a collapsed "Report a bug" with a description box (`MAX_DESCRIPTION_CHARS`), an "Include system info" checkbox (`Settings.include_system_info`, saved with the settings) and Send (`POST /launcher/sessions/:id/report`). A report always names the loader, `HOST_API`, protocol, agent (the loaded client's, or the loader's own `agent.dll`) and lib versions and the platform (`feedback::diagnostics`); with system info on it adds the OS and kernel (`/etc/os-release`, or `cmd /c ver`), arch, CPU count and model, memory, `wine --version` and the wgpu adapter name read at startup. For the running session the report carries the script log's tail (`MAX_LOG_BYTES`, whole lines) and a snapshot taken then (`feedback::read_snapshot`: `backend::state` without `account_name` and `player_name`, plus the inventory and worn item containers 93 and 94, `feedback::snapshot`). Account names are scrubbed from the log: every name the client showed during the run (`App::run_names`, collected from the XP tracker's state reads) and those in the snapshot's read, in any case and with spaces, underscores or hyphens between their parts, become `[account]` (`feedback::scrub`). When a store run ends (`App::keep_run_record`, before the session is ended) the loader reads the client once more, scrubs the log and writes `<data dir>/runs/<session id>.bin`: a `feedback::Record` (title, log, snapshot, end time) sealed like `accounts.bin`, under the same keyring key. A report on an ended session sends that record, or only the description and diagnostics when there is none (another machine, a dead keyring). Records older than `KEEP` (24 hours, the server's window) are deleted at startup and on every write. The loader never shows or stores scores and reports beyond the server's answer.
- Scripts' `http_request` goes through the loader (`src/http.rs`): the injector writes an `HTTPREQ` line, the thread reading the script's output starts `answer_http`, which makes the request on a thread of its own and writes the one line answer back. At most 32 requests run at once across all scripts; past that the answer is an error. The request is only made if its host is on the HTTP whitelist (`src/whitelist.rs`), which Settings edits: the Volcren hosts (those of `api_url`, `supabase_url` and `site_url` in the config) are listed as "Built in" and can't be removed, and "Add URL" opens a dialog for more. An entry is a host (`example.com`, matching any scheme, port and path; a pasted URL is cut down to its host) or `*.example.com` (its subdomains, not the domain itself); Delete needs a second click, as in Accounts. The user's entries are saved in eframe storage (`http_whitelist`), where no script can reach them. Redirects are followed by hand, at most 5, and each hop's host is checked too; `Authorization`/`Cookie` headers aren't sent to a different host than the first, or over `http` when the first request was `https`. The whitelist is copied when the script asks, so a change applies from the next request.
- Terminal is its own sidebar page between Development and Settings (`src/terminal.rs`, `Tab::Terminal`): the user's shell (`$SHELL`, `COMSPEC` on Windows) in the folder the loader was launched from, on a `portable-pty` pseudo-terminal, emulated by `alacritty_terminal` (the engine Zed uses) and drawn cell by cell in egui, so TUIs like Claude Code and Codex work. The shell starts the first time the page opens and lives until the app closes. Ctrl+Shift+C copies the selection and Ctrl+V pastes (Ctrl+V is not sent to the program); Shift+Enter sends a newline. Mouse reports go to a program that asks for them (hold Shift to select anyway).
- Backend endpoints (`api_url`, `supabase_url`, the public `anon_key`, optional `site_url`) are compiled in from `src/loader/config.json` (`api/config.rs`); the `API_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SITE_URL` environment variables override them at run time. There is no `.env`.
- Edits scripts with Luau syntax highlighting.
- Open last (beside Open…, `App::open_last_script`) reopens the file the editor last opened or saved as (`App::last_script`, kept in eframe storage, so it survives restarts and the default script loaded at startup). A file that has gone or can't be read is reported and forgotten, which greys the button out.
- On Run, compares the file on disk with what the editor last synced (`ScriptFile::disk`: set on open, save, startup) and prompts to reload if it changed; the prompt also warns about unsaved edits.
- Dev tools: RuneLite-style checkboxes (`DEV_TOGGLES` in `app.rs`) that draw scene layers through `injector::scene_tiles_next_frame`, once per frame the client presents (`TilesWorker`); a checkbox with no entry in `DEV_LAYERS` isn't ported yet.
- Development has tabs (`DevTab` in `app.rs`): Tools (game state and the checkboxes above) and Inspectors, which holds a tab per inspector (`InspectorTab`: Widget, Var, Script, Inventory, Packet; the names below keep "Inspector" for the thing itself). The Var Inspector, which also holds the collapsed Varps section (read one varp, the known varps, or what changed since the last read) above its log (`Inspector` in `src/vars.rs`: with Enable on, `poll_vars` reads all varps every `POLL_EVERY`, diffs them against the previous read and logs changes under `Tick N` headers like RuneLite's; a changed varp logs its varbits that changed (looked up once per varp with `backend::varbits_of`) and then the varp if bits remain unexplained; the first read, and the first after a logout, is only a baseline; the VarClientInt and VarClientStr boxes list the client variables the scripts change, from the varc log (`injector varc-changes`; the poll job reads it with the varps, the first read only marks the place, and a log that can't be read is a warning, not an error), shown by index since varcs have no names here), the Script Inspector (`Inspector` in `src/script_log.rs`: with Enable on, `poll_script_log` reads the client's script log (`injector scripts <pid> <since>`, `backend::script_runs`) every `POLL_EVERY` and lists a run per row (columns Tick, Script, Arguments, Time) with its duration once the end entry has been read (an end entry belongs to the latest unended row of its depth, and is dropped when a shallower row comes first), nested runs indented, `Trigger <type>` for component and menu events whose script id isn't known, and the tick the run started in on the first run of each tick; scripts show as `Script <id>` until the Load names button is clicked; it downloads RuneLite's `cs2-scripts` repository as one zip on a worker thread (`Names::download` in `script_names.rs`; the cache has no script names, only a hash of each, so nothing is bundled) and keeps `name (id)` for every script it names in memory only, the commit it is from shown under the buttons (the ids are the cache's, so the names are right for the build the repository was decompiled from); the Blacklist box drops scripts, by id or (once loaded) name, as they arrive (default `6697, 4730`, the ones an idle account runs every frame), keeping the last 10000 runs) the Inventory Inspector (`Inspector` in `src/inventory.rs`: with Enable on, `poll_inventory` reads the client's item log (`injector item-changes <pid> <since> <wait ms>`, `backend::item_changes`; the agent hooks the client's container slot writer). A read with nothing new blocks (up to `WAIT_FOR_CHANGE`) on an event the agent sets when it logs a change, so there is no timer: the next read starts when the last one returns, and on Linux the waits go through a helper of their own (`Lane::Events`). The first read marks the place in the log (`injector::ITEM_CHANGES_NOW`) and reads every container once (`injector containers`, `backend::item_containers`) as a baseline; after that the inspector applies the logged slot changes to its own copy and never rescans the containers. A snapshot is the copy after the changes one container got in one game tick, with that tick; a log that skipped changes (overwritten, or a new agent's) makes the next read a baseline again. Container names come from `game-vals` kind INV, item names from `item-names` and stackability from the item definition (`item-stackable`), each looked up once. Like RuneLite's, snapshots wait in a pending list until Refresh moves them into the tree (25 per container, `KEEP`); picking a tick shows what was added and removed against the snapshot before it, summed by item id with a non stackable item listed once per copy, then every slot of the container as its icon in a grid (4 wide for the inventory), the slot, name, quantity and id on hover; the added and removed items get their icons too. Icons come from the icon store (`Icons` in `src/icons.rs`, keyed by `Key::Item` for an item at a quantity with or without its number, or `Key::Sprite` for a sprite of the cache): a picture the UI asks for and doesn't have yet is drawn by the selected client (`backend::item_icons` as the client's inventory draws the item, `backend::sprites` for the cache's sprites; `poll_icons` sends up to `BATCH` at a time, one request in flight) and kept as a texture and in `icons.bin` in the data folder (append-only records with a kind byte, read once at the first use; a file of an older version is started over), so a layout shows its icons on the next start with no client loaded. A read that fails is tried again after `RETRY_AFTER`, keeping what came before the failure. An icon the client couldn't draw is left blank until the loader restarts; the name's first letters show in its place) and the Widget Inspector (`Inspector` in `src/widgets.rs`, `widgets_ui` in `app.rs`: Refresh reads every open interface with `injector widget-tree <pid>` (`backend::widget_tree`; the first look at the tab reads it too) and links it as RuneLite does, each node lettered R (a top of the root interface), S (a component, under the one its parent field names), D (a dynamic child, under its owner) or N (the top of an interface opened inside a component), D before S before N; "Hide hidden" leaves out hidden widgets and their children; the right side lists RuneLite's fields in its order for those the agent reads (id with the group's name from `game-vals` kind INTERFACE, type, content type, parent, self hidden and hidden, text, text colour, opacity, font, text shadow, item id and quantity, sprite, tiling, filled, original position and size, the position and size modes, line height, text alignment, relative position, size, canvas location, bounds, scroll, no click through; `WidgetDetail` in `decode/src/widgets.rs`). The selected widget is boxed in cyan on the client while the tab shows, through the `widget:x,y,w,h,rrggbb` layer of the scene tiles worker. RuneLite's picker widget has no counterpart; "Follow mouse" looks at the client's mouse about ten times a second and selects the smallest widget there instead. RuneLite's other fields (model id, type, animation and rotation, border type, item quantity mode, name, target verb, drag settings, no scroll through, the listeners, ...) are not read yet, and none can be edited) and Packet Inspector (`Monitor` in `src/packets.rs`, `packets_ui` in `app.rs`). The Enable checkbox starts reading: `poll_packets` reads the selected client's packet log (`injector packets <pid> <since>`, `backend::packets`) every `POLL_EVERY` and keeps the last `KEEP` packets, also while another tab is showing. Received and sent packets list as a table (`LogTable` in `app.rs`, which the Var and Script Inspectors use too: a header that stays visible, resizable columns, rows drawn only while shown, long cells clipped) with the columns Time, direction (←/→, sent in the link colour), Opcode, Length, Name, Fields (decoded) and Hex; Received/Sent boxes and the Filter box filter: opcodes or packet names to show, `40, VARP_LARGE`, or to hide, `!40 !PLAYER_INFO` (`Filter` in `src/packets.rs`; a name stands for its packet in one direction and is matched in any case, `UNKNOWN` for every packet without a name). The Names menu next to it (`packet_names_menu` in `app.rs`) lists the known names with a search box, and each click cycles a name through show only, hide and off by rewriting the Filter text, which stays the single source of truth. Follow keeps the list at the newest packet. Clicking a packet shows it in the detail pane: a hex dump with ASCII, the leading bytes as big endian byte/short/int, and Copy hex. Opcodes are raw numbers: they change with game updates. Received packets with a known layout show their fields decoded (value and wire kind) above the hex dump, with their name when there is one, and the identifiers the client's handler touches; a payload that doesn't fit the layout or the expected size is flagged, not guessed at. The layouts come from the client itself: with Enable on, the monitor asks the selected client for what its agent published (`injector packet-layouts <pid>`, `backend::packet_layouts`, once per client and again every 5 seconds until the agent has), and `packet_defs::Table::from_client` turns that into the table `Monitor::table` hands the UI. Until then, and for a client without it, the table shipped in `src/packet_defs.tsv` (generated from the Java client, see [reverse-engineering.md](reverse-engineering.md)) is used; it also supplies names, kept by opcode only while every one of the 151 packet sizes matches the shipped table's (so the opcodes haven't moved; the sent names need that too), and after an update that moved them only for a packet whose size and layout (with fields) are shared with exactly one packet of the shipped table and one of the client's. Packets without a layout stay raw. Sent packets come only from the shipped table, where `names.tsv` names the ones that were worked out (`S<opcode>`, so far only `NO_TIMEOUT`, the keepalive). A sent packet's length excludes its opcode byte.
- Persists `Settings { dll, helper, lib_dir, antiban, transports, include_system_info }` (paths of `agent.dll` and `injector.exe`, and the rest as the pages above describe), auto-detected next to the executable or in `target/x86_64-pc-windows-gnu/{release,debug}`. Also persists the mouse cursor preference (`Cursor`, storage key `cursor`), which is passed to `injector load` so the agent starts with it (the injector leaves it in an `AGENT_CURSOR_<pid>` mapping the agent reads while building its header).

## Layout

| Path | Contents |
| --- | --- |
| `src/app.rs` | The whole UI and its state. |
| `src/script.rs` | Script processes: spawn, stdio pumping, pause, stop, `ScriptEvent` (`Output`, `Form`, `Finished`), and `Process`, the handle a session's thread uses to see the exit, kill the script and take its `report_stats` gains, and `Host`, which the output thread answers PIN, lamp and HTTP requests from (the accounts and whitelist, shared with the UI behind a lock). `app.rs` keeps one `Run` per process. |
| `src/form.rs` | egui rendering of a form spec. |
| `src/api/` | The launcher API: `config.rs` (embedded endpoints), `auth.rs` (PKCE, loopback listener, token exchange/refresh, keyring), `client.rs` (`Api`: blocking calls, 401 refresh-and-retry), `models.rs`, `error.rs` (`ApiError`). Everything blocks, so `app.rs` runs it through `api_job` threads. |
| `src/account.rs` | `Auth` state and the sign-in round trip. |
| `src/http.rs`, `src/whitelist.rs` | A script's HTTP requests (host check, manual redirects, size and time limits) and the HTTP whitelist with its Settings section. |
| `src/accounts.rs` | The Accounts page: entries, hashing, pin check, encrypted file, list and dialog UI. |
| `src/paths.rs` | The shared app folders (`project_dirs`, each store under its own subfolder), the user agent, and Unix seconds. |
| `src/feedback.rs` | Scores and bug reports: the Feedback page and the run page's tab, diagnostics, name scrubbing, snapshots, the sealed run records. |
| `src/store.rs` | The Scripts tab: list, filters, redeem box, community tags, price and balance text, and `Confirmed`, the community warnings the user accepted. |
| `src/update.rs` | Update check: the signed manifest, build comparison, package download. `src/update/archive.rs` is the Linux swap, `src/update/msi.rs` the Windows update, `src/update/msi_command.rs` its `msiexec` arguments and exit codes. |
| `src/session.rs` | Starting a store run: the cache folder (the shared lib, and an empty `<script-id>_<revision>` folder per script that the entry path points into), download into memory with name/checksum checks, pruning; `Beat`, the heartbeat state machine (retries with backoff, give-up, stats pending); and `keep`, which drives a `Beat` on the run's own thread until the script exits and then ends the session. |
| `src/packets.rs` | The packet monitor's buffer and filter (`Monitor`, `Filter`); the UI is `packets_ui` in `app.rs`. |
| `src/icons.rs` | The item icon store: textures, the on-disk file, what is wanted and in flight, and the `slot` widget that draws one. |
| `src/layouts.rs` | Equipment and inventory layouts: the data and its JSON for scripts, per-script storage, the editor tabs and the form's picker. |
| `src/terminal.rs` | The Terminal page: pty session, key and mouse encoding, painting. |
| `src/highlight.rs` | Luau highlighter. |
| `src/backend/mod.rs` | `Settings`, `Target`, `Scan`; re-exports one function set (`connection`, `load`, `state`, `input`, `draw`, ...) from the compiled backend, so `app.rs` is platform independent. |
| `src/backend/native.rs` | Windows: calls the `injector` library directly. |
| `src/backend/wine.rs` | Linux: finds each client's Wine prefix (by the client executable's name, `CLIENT_EXES`), runs one `injector.exe serve` per prefix and talks JSON lines over stdio (`HELPER_TIMEOUT` 45 s). A helper answers one request at a time, so requests that wait for the client's next frame (the dev overlays) go to a second helper of their own (`Lane::Frames`). |

## Gotchas

- The loader depends on the `injector` crate, so the injector's non-Windows stubs must keep compiling.
- On Linux, anything that needs Win32 goes through the Wine helper protocol.
